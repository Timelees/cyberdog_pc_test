# CyberDog2 五人制足球队角色职责、决策与测试方案

## 1. 文档目标与实现基线

本文依据 `football_navigation` 当前源码编写，目标是回答三个问题：

1. 一支 5 台机器人队伍中，每个角色具体做什么。
2. 当前代码如何分配角色、如何生成目标，以及建议如何把决策完善为可比赛的策略。
3. 如何用自动化测试、十机仿真和实机测试验证角色唯一性、战术正确性与安全性。

当前角色集合为：

| 角色 | 数量 | 当前输出名称 | 核心任务 |
| --- | ---: | --- | --- |
| 前锋 | 1 | `STRIKER` | 争夺球权、到球后方、对准对方球门、触球并推进 |
| 支援 | 1 | `SUPPORT` | 在球后侧翼提供接应点，填补前锋失位并准备二点球 |
| 左后卫 | 1 | `DEFENDER_LEFT` | 防守本方左侧通道，拦截回传和对方推进 |
| 右后卫 | 1 | `DEFENDER_RIGHT` | 防守本方右侧通道，与左后卫保持横向覆盖 |
| 守门员 | 1 | `GOALKEEPER` | 守住本方球门中心，根据球的横向位置移动 |

源码基线：

- 角色权威：`src/coordination/football_team_role_assigner.cpp`。
- 球融合：`src/coordination/football_ball_fusion.cpp`。
- 角色目标执行：`src/control/football_goal_adapter.cpp`。
- 导航目标转发和动作控制：`football_trajectory_adapter`、`football_tracking_action_client`。
- 多机避障：`football_multi_robot_obstacle_layer`；轻量仿真使用 `football_simulation_navigator`。
- 当前 `football_team_simulation.launch.py` 是空文件，尚无可直接启动的十机角色闭环入口；测试方案因此包含补齐测试夹具/launch 的步骤。
- 当前源码树没有正式的 `test/` 自动化测试目录，不能把一次空的 `colcon test` 当作通过。

## 2. 当前系统的输入、输出和安全门控

### 2.1 关键输入

| 输入 | 类型 | 作用 |
| --- | --- | --- |
| `/football/ball_pose` | `geometry_msgs/PoseStamped` | 已校验或融合的全局球位姿，坐标系必须为 `tag_global` |
| `/global_vio/<namespace>/odom` | `nav_msgs/Odometry` | 10 台机器人的全局位姿、速度和时间戳 |
| `/football/match_state_command` | `std_msgs/String` | `STOP`、`READY`、`PLAY`、`KICKOFF_A`、`KICKOFF_B`、`FINISHED` |
| `/football/goal_scored` | `std_msgs/String` | 进球后触发对方开球和角色复位 |
| `/football/role_authority` | `std_msgs/String` | PC 角色权威心跳和重复权威检测 |

### 2.2 关键输出

| 输出 | 作用 |
| --- | --- |
| `/football/team_a/striker`、`/football/team_b/striker` | 每队当前唯一前锋 namespace |
| `/<robot>/football/role` | 每台机器人的角色或 `STOP` |
| `/<robot>/football/tactical_target` | 非前锋战术目标；前锋当前也会收到球位置，但由前锋状态机使用球和 kick target 重新计算控制目标 |
| `/football/team_a/kick_target`、`/football/team_b/kick_target` | 球应被推进到的对方球门中心 |
| `/football/team_role_status` | 当前前锋、活动状态或安全停车原因 |
| `/football/match_state` | 经权威确认的比赛状态 |

### 2.3 运动许可采用 fail-closed

以下任一条件不满足时，角色权威向机器人发布 `STOP`，下游撤销有效控制目标：

- 比赛状态不允许本队移动。
- 球数据缺失或超过 `ball_timeout_sec`。
- 权威节点发现另一个新鲜的角色权威实例。
- 在线机器人少于 `minimum_other_robot_count + 1`，默认必须有完整 10 路新鲜 odom。
- 有效机器人位姿时间差超过 `max_pose_skew_sec`。
- 允许移动的队伍没有合法前锋。
- 单机器人 GoalAdapter 缺少本机 odom、9 台 peer odom、角色、战术目标、kick target 或必要 TF。

角色选择与运动许可是两个不同契约：某队可以从剩余在线队员中重新选前锋，但完整队伍障碍数据不满足时仍然必须全队停车。

## 3. 五个角色的具体任务和当前决策

以下坐标约定：A 队进攻目标默认为 `(8, 0)`，本方球门为 `(-2, 0)`；B 队相反。令进攻方向 `d` 为 A 队 `+1`、B 队 `-1`，球位置为 `(xb, yb)`。

### 3.1 前锋 `STRIKER`

具体任务：

- 在本队中承担唯一主动争球权职责。
- 先到达球与对方球门连线后方的接近点，不从侧面或正面撞球。
- 调整航向对准 kick target，稳定建立正面接触。
- 在推进走廊无障碍、接触和姿态均有效时推球。
- 球丢失、角色丢失、走廊阻塞、接触丢失或姿态持续超差时立即停止或重新接近。

当前选人算法：

1. 在有效队员中计算机器人到球的平面距离，选择最近者。
2. 当前前锋失联时，最近者立即接管。
3. 当前前锋至少保持 `striker_min_hold_sec = 1.5 s`。
4. 挑战者只有满足 `挑战者距离 + 0.45 m < 当前前锋距离` 才具有切换收益。
5. 同一挑战者连续保持优势 `striker_switch_confirm_sec = 0.8 s` 后才切换。
6. A 队可通过 `forced_team_a_striker_namespace` 强制指定前锋，强制对象失联则不降级选其他人，而是清空 A 队选择并安全停车。

当前动作决策由 GoalAdapter 完成，主要状态序列为：

```text
NAV_TRANSIT / OBSTACLE_APPROACH
          -> BALL_APPROACH
          -> ALIGN_TO_GOAL
          -> CONTACT_ACQUIRE
          -> PUSH_BALL

任意运动阶段 --障碍过近/推进走廊阻塞--> BLOCKED_RECOVERY
任意阶段 --输入、角色或比赛状态无效--> SAFE_STOP
```

关键约束：进入推球默认要求横向误差不超过 `0.08 m`、航向误差不超过 `0.10 rad`；退出阈值为 `0.14 m` 和 `0.18 rad`，形成迟滞。`CONTACT_ACQUIRE` 和 `PUSH_BALL` 禁止横移，只允许机体前向速度和航向修正。

### 3.2 支援 `SUPPORT`

具体任务：

- 保持在前锋和球的后侧，不抢占前锋球后接近线。
- 提供侧后方接应点，接收回传或争抢被挡出的二点球。
- 当前锋失联或明显失去球权时，成为最有条件接管前锋的候选。
- 防止所有非前锋都退到本方球门附近，保持攻守连接。

当前目标公式：

```text
x = xb - d * 1.0
y = yb + 1.4
```

这意味着 A、B 两队的支援都固定在球的 `+Y` 一侧，仅 X 方向随攻向镜像。目标会被裁剪到场地边界内 `0.30 m` 的安全区域。

当前限制：没有根据边线、对手、空闲侧、传球线或支援机器人能力选择左右侧；球靠近上边线时容易把目标夹在边界附近。

### 3.3 左后卫 `DEFENDER_LEFT`

具体任务：

- 守住本方左侧防守通道，优先阻断球到本方球门的左侧路径。
- 与右后卫形成横向覆盖，避免两者追同一目标。
- 球进入本方半场时适当前压，但不得越过球形成身后空当。
- 前锋和支援均失去球权时，延缓对手而不是盲目争球。

当前目标公式：

```text
x = 本方球门X + d * 1.2
y = -1.1
```

注意：代码中的 `DEFENDER_LEFT` 固定使用负 Y。这里的“左”是全局场地坐标含义，不一定是机器人面向进攻方向时的视觉左侧，B 队使用时需要在战术定义中统一命名。

### 3.4 右后卫 `DEFENDER_RIGHT`

具体任务：

- 守住与左后卫相对的通道，覆盖本方禁区右侧。
- 维持后防宽度，在球横向转移时与左后卫轮换压迫和保护。
- 避免进入守门员门线活动区域，也不进入前锋推球走廊。

当前目标公式：

```text
x = 本方球门X + d * 1.2
y = +1.1
```

当前限制：左右后卫位置完全静态，不随球的 X/Y、球速和对方位置调整，也没有“一个上抢、一个保护”的联动状态。

### 3.5 守门员 `GOALKEEPER`

具体任务：

- 始终位于本方球门前方，优先覆盖球到球门的射门线。
- 沿球门横向移动，但不离开设定的守门区域。
- 球远离本方半场时保持门前，不参与普通前锋竞选。
- 球进入门前危险区时做封堵；当前系统只提供站位导航，不包含扑救、踢解围或身体动作决策。

当前目标公式：

```text
x = 本方球门X + d * 0.35
y = clamp(yb, -0.7, +0.7)
```

目标同样经过全场边界裁剪。当前限制是只跟随球的 Y 坐标，没有按“球到球门中心射线”的交点站位，也未考虑球速、射门时间和门柱安全距离。

## 4. 当前角色绑定规则

前锋选出后，其余有效机器人按 `cyberdog_N` 的数字编号从小到大排序，并依次绑定：

```text
第 1 个剩余机器人 -> SUPPORT
第 2 个剩余机器人 -> DEFENDER_LEFT
第 3 个剩余机器人 -> DEFENDER_RIGHT
第 4 个剩余机器人 -> GOALKEEPER
```

因此目前只有前锋是动态竞选结果，其他职责不是基于位置、路径成本、剩余电量、故障状态或角色切换成本决定的。某非前锋离线后，编号靠后的机器人会整体向前补位；完整十机运动许可检查随后会因数据不足而发布全队 `STOP`。

每个更新周期对每台机器人只发布一次角色消息，避免先发 `STOP` 再发活动角色导致 Action Client 每周期取消健康目标。

## 5. 建议的完整角色决策实现

建议保留现有安全门控和前锋迟滞，在其上增加“比赛层、角色分配层、角色行为层”三层决策。所有建议应分阶段实现，不能以新策略绕过 fail-closed。

### 5.1 比赛层

先根据比赛状态确定允许的战术模式：

| 比赛状态 | 本队行为 |
| --- | --- |
| `STOP`、`READY`、`FINISHED` | 全队 `STOP`，清除进行中的角色切换 |
| 本队 `KICKOFF` | 开球保持期内停车；保持期后只有本队可运动，球移动 `0.25 m` 或超时后转 `PLAY` |
| 对方 `KICKOFF` | 本队停车，不能提前抢球 |
| `PLAY` | 进入正常角色分配和行为决策 |

建议再由球所在区域选择阵型：本方危险区用 `1-2-1` 防守结构，中场使用当前均衡结构，对方危险区让支援前压但守门员和至少一名后卫留后。

### 5.2 角色分配层

对每个有效机器人 `r` 和角色 `k` 计算代价，使用 5x5 最小代价匹配；规模固定，可枚举 120 种排列，也可用 Hungarian 算法。

建议代价：

```text
C(r,k) = wd * 到该角色目标的路径距离
       + wy * 到目标后的航向调整代价
       + ws * 角色切换惩罚
       + wr * 路径风险/障碍密度
       + wb * 电量或健康惩罚
       + wg * 角色专属惩罚
```

角色专属约束：

- `STRIKER`：重点使用到球后接近点而不是到球心的路径时间；保留当前 1.5 s 保持、0.45 m 收益、0.8 s 确认迟滞。
- `SUPPORT`：比较球两侧候选点，选择边界净空、对手净空和传球线更优的一侧。
- `DEFENDER_LEFT/RIGHT`：分别覆盖球到本方门的两个通道；交换两个后卫时应有切换惩罚，防止交叉跑位。
- `GOALKEEPER`：默认保持固定机器人身份，除非失联或健康异常；加入很高的离岗和换岗惩罚。

角色分配结果必须满足：每个角色恰好一个机器人、每台机器人恰好一个角色、无效机器人只能为 `STOP`。新分配连续稳定若干周期后再提交；前锋失联和守门员失联可走紧急接管路径。

### 5.3 角色行为层

#### 前锋目标

使用当前 GoalAdapter 状态机，不直接导航到球心。球后点为：

```text
u = normalize(kick_target - ball)
behind = ball - approach_distance * u
```

目标越界或球与 kick target 太近时安全停止。推进走廊被占用时进入 `BLOCKED_RECOVERY`；在实现带球绕障前，不允许从障碍物中穿过。

#### 支援目标

生成两个候选点：

```text
support_left  = ball - 1.0*d + 1.4*n
support_right = ball - 1.0*d - 1.4*n

默认优先选择远离最近边线的一侧；若球在上半场选择 `support_right`，否则选择
`support_left`，再由边界、对手和传球线代价进行覆盖。
```

其中 `n` 为进攻方向法向量。按边界净空、离对手距离、与前锋距离、传球线遮挡和到达时间评分，选择低代价点。若前锋进入球后接近线，支援点必须在该走廊外。

#### 后卫目标

令 `home_goal` 到球的方向为 `q`，在本方球门前设置随球推进的防守线：

```text
defense_x = clamp(home_goal_x + d * (1.0 + kx * danger), 合法防守区)
center_y  = clamp(ky * ball_y, -1.2, 1.2)
left_y/right_y = center_y +/- spacing/2
```

离球更近且路径更短的后卫负责压迫，另一名后卫保护球门方向；只有连续优势超过阈值才交换职责。

#### 守门员目标

求球到本方球门中心射线与守门员活动线 `x = home_goal_x + d*0.35` 的交点，得到目标 Y，再裁剪到门柱内安全范围。加入球速后，可使用短时预测球位，但预测目标必须有最大移动速度和低通滤波，防止观测抖动造成门前振荡。

### 5.4 目标去冲突

角色目标生成后统一执行：

1. 裁剪到场地和角色合法区域。
2. 检查任意两个目标之间至少保留机器人碰撞椭圆和额外安全净空。
3. 检查目标路径不穿过足球保护圆、前锋推进走廊或守门员专属区。
4. 冲突时按 `GOALKEEPER > STRIKER > 防守保护位 > SUPPORT` 的优先级保留高优先级目标，低优先级角色选择备用候选点。
5. 目标位置和角色变化增加迟滞、最小保持时间及最大更新频率。

## 6. 测试基础设施方案

### 6.1 建议新增的测试组件

- `test/test_football_geometry.cpp`：纯几何和距离选择单元测试。
- `test/test_team_role_assigner.cpp`：用 ROS 2 测试节点发布球、10 路 odom、比赛状态和权威消息，订阅所有角色输出。
- `test/test_ball_fusion.cpp`：构造多机器人本地检测、odom、离群点和时间差。
- `test/test_role_goal_adapter.cpp`：分别为五种角色喂入战术目标，验证控制状态和 approach pose。
- `test/football_team_roles.launch.py`：十机角色集成测试夹具，不依赖实机。
- `launch/football_team_simulation.launch.py`：补齐可人工观察的十机仿真入口；测试夹具和演示 launch 应分开，避免断言依赖 RViz。
- `scripts/analyze_team_role_bag.py`：离线统计角色唯一性、切换次数、目标间距、状态超时、最小碰撞净空和完成时间。

在 CMake 中显式注册 gtest/launch test，并用 `colcon test-result --verbose` 确认实际生成 XML、测试数非零且时间戳属于本次执行。

### 6.2 每个用例必须采集的证据

```text

/football/team_role_status
/football/team_a/striker  或 /football/team_b/striker

```

每次测试保存：源码 commit 或 source digest、参数快照、rosbag2、节点日志、分析 JSON/CSV；实机测试另存现场视频和急停记录。

### 7.2 节点集成测试

## 8. 十机仿真测试方案

### 8.1 测试阶段和通过门槛

先用理想定位和静态障碍验证角色，再逐步增加动态和异常因素。每个场景至少运行 60 s，固定随机种子并重复 20 次；切换边界用例需单独重复 100 次。

全局通用门槛：

- 任意时刻每队最多一个 `STRIKER`，活动时恰好一个。
- 同一队活动角色不重复，且一台机器人不能同时承担两个角色。
- 角色或输入失效后 `0.4 s` 内不再出现非零运动命令；具体上限应取更新周期、消息超时和底盘制动延迟之和，并在实机重新标定。
- 非故障稳态下前锋切换频率小于每分钟 3 次；等距抖动场景不得来回切换。
- 任意两台机器人的外接椭圆不得相交；规划最小净空不低于配置的路径安全阈值。
- `CONTACT_ACQUIRE` 和 `PUSH_BALL` 中 `cmd_vel.linear.y == 0`。
- 所有 tactical target 在场地安全边界内，目标之间不应重合。

## 9. 分角色验收用例

### 9.1 前锋

1. 将前锋放在球后 2 m，其他机器人不阻挡。
2. 确认状态依次进入接近、对齐、触球和推球阶段。
3. 在对齐阶段分别注入 `0.05/0.10/0.15/0.20 m` 横向偏差和 `5/10/15 度` 航向偏差。
4. 在推球阶段让球横向偏移、突然前滚、被障碍卡住和观测消失。
5. 验收：小误差收敛；超过退出阈值后重新对齐；接触或进展 watchdog 到期后停止；球最终沿 kick target 方向前进。

### 9.2 支援

1. 球分别位于场地中心、上下边线和两个进攻角。
2. 前锋沿球后接近线移动，支援同时到当前公式目标。
3. 验收当前实现：目标等于 `(xb-d*0.8, yb+0.8)` 经边界裁剪后的结果，状态为 `TACTICAL_SUPPORT`。
4. 验收升级策略：两个侧翼候选中选择净空更大者；不能侵入前锋接近/推进走廊；球换边后经过迟滞才换侧。

### 9.3 左右后卫

1. 球从中线沿左、中、右三条通道向本方球门移动。
2. 分别安排一名对手从左右通道推进。
3. 验收当前实现：两个目标始终在防守 X 线、Y 为 `-1.1/+1.1`，不发生角色重复。
4. 验收升级策略：近侧后卫上抢、远侧后卫保护；两者不交叉、不同时追球；对手换边时切换次数受迟滞约束。

### 9.4 守门员

1. 球 Y 从 `-2 m` 匀速移动到 `+2 m`，覆盖静止、慢速和快速来球。
2. 验收当前实现：守门员 X 固定为球门前 `0.35 m`，Y 始终在 `[-0.7,+0.7]`。
3. 验收升级策略：守门员位于球门中心射线上，目标速度有限且不振荡；不得离开守门区域或参与普通争球。
4. 射门扑救动作不属于当前导航实现，不能仅凭站位测试宣称扑救功能通过。

## 10. 实机分阶段测试

### 10.1 前置条件

- 每台机器人已单独验证急停、底盘限速、定位和 Nav2 停车。
- 10 台设备时钟同步，所有 odom 使用 `tag_global` 且时间戳新鲜。
- PC 侧只运行一个 ball fusion 和一个 role authority。
- 每台机器人能收到自身角色、战术目标、本队 striker、kick target 和另外 9 台 odom。
- 先用 `enable_motion:=false` 验证接口，再显式启用运动。

### 10.2 递进顺序

1. 1 台前锋、其余实体不上场：只验证状态机和紧急停车。
2. 1 队 5 台，球静止：验证角色输出和静态站位，限速不高于 `0.15 m/s`。
3. 1 队 5 台，球缓慢移动：验证角色目标更新和同队避碰。
4. 双方各 2 台：验证对手障碍感知和争球安全。
5. 双方各 5 台，静态开球：验证完整角色和比赛状态。
6. 双方各 5 台，动态比赛：最后才验证竞争、切换和异常恢复。

每级必须连续通过 10 次且没有急停、碰撞、越界和数据超时，才能进入下一级。任何安全异常都记录为失败，不能用后一次成功覆盖。

### 10.3 实机验收指标

- 急停端到端延迟、角色丢失停车延迟和球丢失停车延迟均实测并小于现场安全预算。
- 角色消息稳定，无单周期重复角色或短暂双前锋。
- 机器人中心和外接椭圆不越界，任意两机保持现场规定的最小净空。
- tactical target、实际轨迹和最终站位误差均有量化记录；建议非前锋稳态位置误差不超过 `0.20 m`。
- 前锋角色切换后旧前锋的活动目标被取消，新前锋在安全门控满足后接管。
- DDS 丢包、PC 权威重启、单机断网、定位漂移和时钟偏差均能触发安全停车。

## 12. 实施优先级

1. 先补齐角色分配与 fail-closed 的自动化节点测试，这是修改战术前的回归基线。
2. 补齐十机 `football_team_simulation.launch.py`，让五角色目标和双方前锋竞争可重复运行。
3. 将非前锋从“编号绑定”升级为带切换惩罚的最小代价分配。
4. 先完善支援换侧、后卫压迫/保护和守门员射线站位，再考虑更复杂的传球和带球绕障。
5. 完成仿真异常矩阵后，按低速、少机器人到完整十机的顺序进行实机验收。

在上述第 1、2 项完成前，当前实现可用于验证接口和基础站位，但不应宣称已经完成五角色协同比赛能力。
